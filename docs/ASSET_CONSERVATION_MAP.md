# 资产守恒与结算边界

本文是 v0.4.1 的资产端点清单。除明确标注的发行/销毁事件外，业务操作必须保持货币、商品或证券各自守恒；价格变化不等于资产发行。

## 权威端点

| 资产 | 权威端点 |
| --- | --- |
| 货币 | 玩家可用/冻结账户、NPC 市场账户、央行储备、公司现金、银行准备金与客户子账、合同/融资/公司行动/基金/期货/保险托管账户 |
| 商品 | 玩家真实背包、玩家/公司 custody、公司 legacy inventory、NPC 库存、订单冻结库存 |
| 证券 | 玩家可用/冻结持仓、基金持仓、库存股、系统流动性、债券/票据/期货仓位 |

央行政策投放、管理员 `/finance give`、初始账户资金和公司生产输出是显式来源；手续费、生产消耗、破产无法覆盖的已确认损失是显式去向。它们必须有类型化记录，不能伪装成普通转账。

## 跨端点操作矩阵

| 操作 | 来源 → 去向 | 提交前检查 | 提交、回滚与幂等 |
| --- | --- | --- | --- |
| 玩家转账/市场成交 | 买方可用或冻结 → 卖方可用 | 正数、乘法无溢出、余额及收款容量、库存/持仓 | 服务层原子结算；失败不推进订单；成交记录是唯一成功凭据 |
| 商品挂单/撤单 | custody ⇄ 冻结库存；资金 ⇄ 冻结资金 | 商品、数量、价格、所有权 | 下单先冻结；撤单精确解冻；订单 UUID 防重复 |
| 仓库存入 | 背包 → 玩家/公司 custody | 终端身份、距离、权限、容量、物品无特殊 NBT、槽位快照 | 先规划并复核背包移除，再入 custody；入账失败恢复物品；玩家 UUID + operation key 幂等 |
| 仓库提取 | custody → 背包 | 同上并检查背包完整容量 | 先规划插入，再扣 custody；插入失败恢复 custody；允许从超容量/停用仓库安全取回 |
| NPC/公司采购合同 | NPC 账户或公司现金 → escrow → 玩家 | 发布额度、期限、商品、发行方资金；交付时检查真实物品、收款容量、escrow 精确余额 | 发布失败原路退回；交付失败恢复商品；到期只向发行方退款一次；合同 operation key + 状态幂等 |
| 公司生产 | 输入 custody/legacy + 公司现金 → 输出 custody + 运营成本去向 | 同日标记、风险状态、原料、输出容量、维护费 | 全批次提交；失败恢复材料和现金；设施 lastProcessedDay 防双产 |
| 公司融资/债券/贷款 | 投资者/银行 → 托管或公司；到期反向 | 额度含认购中债务、股本/金额上限、收款容量 | 合约状态机与独立 escrow；失败退款；利息与本金逐期记录 |
| 实体资本项目 | 公司/真实融资 → 项目 escrow → 明确升级成本去向；custody/背包 → 施工消耗 | 治理授权、融资真实状态、escrow 精确余额、材料、设施身份、距离、等级和权限 | 预算/材料创建时冻结；施工失败恢复原端点；取消只退未使用 escrow，不撤销既有贷款/债券；项目与设施 operation key 双重幂等 |
| NPC 投资者注资 | NPC 资金池 → NPC 投资者账户（`NPC_INVESTOR_FUNDING`） | 资金池扣除后不低于 `poolReserveFloor`；投资者账户先以系统账户建立，不领新手资金 | 同一 MC 日只执行一次；资金池不足时跳过，不透支 |
| NPC 残差配售 | NPC 投资者资金 → 销毁（`NPC_FLOAT_PLACEMENT`，显式去向）；系统流动性残差 → 投资者持仓 | 仅 NPC 投资者账户；残差股本核对一致且足量；单原型、NPC 合计、每日成交三道上限 | 先扣款再入持仓，入持仓失败退款；配售款不付给公司（IPO 已按全部发行量铸造募资） |
| 宏观经济工资 | 公司现金 → 聚落预算账户（`MACRO_WAGE`） | 按工资只雇付得起的人数；存款失败退回公司 | 同一 MC 日只招工发薪一次 |
| 宏观经济回流 | 聚落预算账户 → NPC 资金池（`MACRO_VILLAGE_SPENDING`） | 只转出超过补足上限两倍的部分 | 日结幂等标记 `LastProcessedDay` |
| 央行商品平准 | 央行 ⇄ 国际市场：商品在两边库存之间转移，货款按市价反向转移（`CENTRAL_BANK_STABILIZATION`） | 卖出只动央行已有储备，国际市场付不起的部分央行不收；收储时央行余额不足先扩表；市场库存低于参考量一半不收 | 每种商品每天一次，数量不超过参考库存的 `stabilizationMaxDailyBps` |
| 公开市场操作 | 商业银行总账内：准备金 ⇄ 央行票据（`ASSET_BOND`）或回购款（`LIABILITY_CENTRAL_BANK`），不经过玩家钱包 | 只吸收超额准备金；回购只借给权益为正的银行；每行每天不超过存款的 `openMarketMaxDailyBps` | 引用号按银行 + 动作 + 日期确定，同一天不重复记账 |
| 旧国库并入 | 旧国库账户 → 央行（`LEGACY_TREASURY_MERGE`） | 只转移国库现有余额，国库对央行的债务注销 | 余额为 0 后不再执行 |
| 商队进口实物 | 抽象市场 → 目的地聚落托管 | 聚落托管只能被人口消费，玩家无法提取 | 每趟货运结算一次（与卖出货款同一次） |
| NPC 竞争公司新建 | NPC 资金池 → 新公司现金（`RIVAL_SEED`） | 无主公司数低于上限、冷却期已过、资金池扣除后不低于 `poolReserveFloor` | 先扣资金池再入公司，入账失败退回；同一 MC 日只执行一次 |
| NPC 竞争公司升级 | 公司现金 → NPC 资金池（`RIVAL_UPGRADE`，视为采购建材） | 现金 ≥ 升级费 × 人格倍数、距上次升级 ≥ 7 天 | 升级失败退回公司现金 |
| NPC 竞争公司建仓/要约 | 公司现金 → 投资账户（`RIVAL_INVESTMENT`）→ 残差配售（销毁）、普通买单或要约 escrow | 公司转出后至少留 2 万现金；投资账户以系统账户建立；要约走 `TakeoverService` 全部校验 | 存款失败退回公司现金；要约失败或交割后按要约规则原路处理 |
| NPC 公司上市 | 发行铸造 → 公司现金；上市费从公司现金销毁；创始股 → 确定性投资账户 | 仅 `ownerId == null`；发行价、发行量、`MAX_TOTAL_RAISE` 与玩家 IPO 完全相同 | 与玩家 IPO 同样的回滚顺序；投资账户以系统账户建立，不领新手资金 |
| 分红/清算 | 公司现金 → 股东/债权人 | 全部收款容量、登记日权重、可分配金额 | `BigInteger` 比例分配 + 确定性余数；任何预检失败不退市、不删除债权 |
| 回购/要约/重组 | 公司/买方 escrow ⇄ 股东股份或卖方库存 | 已通过授权、双方权限、资金/股份/库存全量预检 | 原子交割；失败保留可重试任务；取消原价/原成本退回；行动与授权 ID 幂等 |
| 银行/基金/期货/保险 | 钱包、准备金、子账和各产品托管之间 | 复式平衡、保证金/准备金、头寸及收款容量 | 使用账本批次或明确补偿；重启恢复同一 reference 不重复记账 |
| 运输 | 仓库 custody → 运输 custody → 目标 custody/合同发行方 | 源/目标身份、权限、容量、令牌和整批数量 | 货箱 NBT 不保存权威数量；损毁保留托管并轮换令牌；重复卸货无效 |
| 聚落需求 | NPC 账户 → 需求 escrow → 玩家；背包 → 聚落 custody | 贸易站、期限、接受者、真实物品和收款容量 | 资金与物品原子提交；拆站不删除 escrow；过期精确退款 |
| 探索调查 | NPC 账户 → 调查 escrow → 玩家 | 有界已登记目标、冷却、期限、真实方块交互和收款容量 | 凭证只含任务 UUID；取消/失效/过期退款；重复到达不付款 |
| 库存质押贷款 | 银行贷款资产/公司存款；公司 custody 中的 reservation 不转移所有权 | 公司角色、实体银行柜台、可靠价格、未质押可用量、银行集中度与资本 | 放款失败完整释放 reservation；还款按本金释放；清算才把商品移入协议 custody，卖不掉则保留商品与债权 |
| 经营对冲目标 | 无资产移动；只读关联个人保证金账户中的真实期货仓位 | 公司经营权限、同商品合约、目标数量、截止日与方向 | 创建/取消目标不下单、不转钱；真实仓位变化才改变覆盖率，个人盈亏不进入公司财报 |
| 世界化保险 | 投保人/银行 → 保险池 → 公司或贷款银行 | 真实可用 custody、设施连续状态、财务历史、抵押审计回收 | 事件创建失败恢复库存；质押库存不重复赔付；抵押回收先冲减贷款，再按净损失理赔 |

## 审计结论

- 新仓库、合同和公司经营路径没有把普通 `deposit`/`addCommodity` 当成无来源奖励；测试覆盖失败补偿、重复请求、到期退款和重启恢复。
- `setBalance`/直接恢复方法只用于初始化、存档恢复和测试夹具；管理员发行有独立权限与交易类型。
- 仓库方块的所有移除方式现在都会把物理端点设为 `DISABLED`，但不会删除 custody，管理员或玩家仍可按恢复流程取回。
- 后续新增跨端点操作必须先更新本表，并至少添加“失败不移动任一侧”和“重复调用不二次支付”测试。
